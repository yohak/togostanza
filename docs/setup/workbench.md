# 検証領域セットアップ

`workbench/` は、CLI実行確認と将来の現行版/リメイク版比較に使う検証領域。

これは使い捨てのサンドボックスではない。現行版とリメイク版の検証環境を分け、同じ検証ケースを両方で比較できる構造を保つ。

仕様確認のために作って壊す作業は `sandbox/` で行い、再現可能な検証手順として残す段階で `workbench/` に移す。

## 役割

- 現行版CLIを実行する検証環境を置く。
- リメイク版CLIを実行する検証環境を置く。
- 再現可能なCLI検証ケースを手順として定義する。
- `references/` を汚さずに現行版CLIの確認を行う。
- 後で同じ検証ケースに対してリメイク版CLIの確認を行う。
- 比較のため、生成物をローカルに保持する。

## 初期方針

- `workbench/` 自体はプロジェクト構造の一部とする。
- `workbench/current/` と `workbench/remake/` は、それぞれ Stanza群プロジェクトとして扱う。
- 検証ケースは `workbench/cases/` 配下の手順ファイルとしてGit管理する想定とする。
- `node_modules/` と生成物は、形が分かり次第Git管理から除外する。
- 既存挙動調査の前に、具体的な検証ケースを増やしすぎない。

## 想定レイアウト

```text
workbench/
  current/
    package.json
    ...
  remake/
    package.json
    ...
  cases/
    build-basic.md
    build-with-css.md
```

## 検証ケースの形

検証ケースは、Stanza群プロジェクトそのものではなく、`workbench/current/` と `workbench/remake/` に対して同じ確認を行うための手順・観測定義として扱う。各検証ケースでは次の関係が分かるようにする。

- 入力条件
- 観測対象のコマンド
- 現行版の出力
- リメイク版の出力
- メモと重要なログ抜粋

## 人間へ相談する条件

検証ケースの実行にNode/npm/pnpm、依存関係、lockfile、ソースの変更が必要になりそうな場合は、変更前に停止して人間へ相談する。
